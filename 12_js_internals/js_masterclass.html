JavaScript, under the hood

Everything the earlier lessons in this repo showed you what JavaScript does. This page shows why: the engine, the call stack, memory, prototypes, the event loop, the DOM, Node, the weird edge cases, and the C++ inside V8 that makes it all happen.

How to use this page Code blocks with a ▶ Run button execute for real in your browser (output appears under the block, just like console.log). Panels with Step ▶ are simulations — step through them slowly and read the yellow note each time. Repo files are tagged like 01_basics/04_comparision.js: open them side by side.

The one picture to remember

A JavaScript engine (V8 in Chrome/Node, SpiderMonkey in Firefox, JavaScriptCore in Safari) only knows the language: it has a heap for objects and a call stack for running functions. Everything else — timers, the network, the DOM, files, and even the event loop itself — is provided by the host (the browser or Node).

01

How JavaScript actually runs

JavaScript is often called "interpreted". Modern engines are really multi-tier JIT compilers. V8 reads your code, turns it into bytecode, runs that bytecode in an interpreter while watching the types it sees, and compiles the hot functions to optimized machine code — betting that the types will stay the same. If the bet fails, it deoptimizes back to bytecode.

V8's tiers (2023+). Folder names refer to the V8 source tree (see §16).

Real bytecode for a function from this repo

This is 03_basics/01_functions.js addTwoNumbers — captured from Node v22 (V8 12.4) with node --print-bytecode --print-bytecode-filter=addTwoNumbers file.js:

Ignition is a register machine with an accumulator. Notice [0]: every operation that can see different types has a feedback slot. After addTwoNumbers(3, 5) slot 0 says "Smi + Smi" (small integers). The optimizing compilers read that and emit a single CPU add instruction plus an overflow check.

Senior takeaway Speed in JS comes from predictability: functions that always receive the same types and the same object "shapes" stay optimized (monomorphic). Mixing types in hot code, adding properties in different orders, or delete-ing properties makes the engine fall back to slower generic paths. You'll see the mechanics in §16.

Execution context, hoisting & the call stack

Whenever JS runs code it creates an execution context (EC): one Global EC for the file, then a new Function EC for every call. Each EC is built in two phases:

1 · Creation (memory) phase

Scan the code, create bindings: var → undefined, function declarations → the whole function, let/const/class → uninitialized (TDZ). Decide this. This is what people call hoisting.

2 · Execution phase

Run line by line, assign values, and for every function call push a new EC on the call stack; when it returns, pop it. The stack is LIFO and there is only one per thread.

Stack overflow, live

The call stack has a fixed size (V8's default is about 1 MB, set by --stack-size). Recursion without a base case keeps pushing frames until the engine throws RangeError: Maximum call stack size exceeded. JS engines do not do tail-call optimization (only Safari implements the ES2015 proper-tail-call rule).

Engine detail "Primitives live on the stack, objects on the heap" is a good mental model, not how V8 really works. V8 keeps locals in registers/stack slots when it can, but any variable captured by a closure goes into a heap-allocated Context object, numbers that aren't small integers become heap HeapNumbers, and the optimizer can delete objects entirely (escape analysis). The model is still the right way to reason about copy vs reference — next section.

Values, references, null & undefined

From 01_basics/datatypes-summary.js: JS has 7 primitive types — string, number, boolean, null, undefined, symbol, bigint — and one non-primitive type: object (arrays, functions, dates, maps… are all objects).

Primitives

Immutable. Compared by value. Copying copies the value. "abc".toUpperCase() returns a new string — the old one never changes.

Objects (references)

Mutable. Compared by identity ({} === {} is false). A variable holds a reference (an address) — copying it gives a second name for the same object.

The spec defines a few abstract operations that every operator uses: ToPrimitive, ToNumber, ToString, ToBoolean. Learn these four and nothing in this section is "weird" anymore. ToPrimitive(obj) calls obj[Symbol.toPrimitive] if present, else valueOf() then toString() (order flips when a string is preferred). The + rule: convert both sides to primitives; if either is a string → concatenate, otherwise → add numbers. Every other arithmetic operator always converts to numbers.

05

Scope, the scope chain & closures

Lexical scope means a variable's visibility is decided by where the code is written, not where it is called from. Each function/block creates a lexical environment (a record of its variables + a pointer to the outer environment). Looking up a name walks outwards along that chain — never inwards.

Closures

A closure is a function bundled with a reference to the environment it was created in (spec: the [[Environment]] internal slot). When makeFunc() returns, its execution context is popped off the stack — but the environment stays alive on the heap because displayName still points at it.

The most famous closure bug: var in a loop

Closure memory gotcha (V8 specific) V8 allocates one shared Context object per scope for all variables that any inner function captures. If two closures are created in the same scope and one captures a huge array, the other — even a tiny long-lived event handler — keeps that array alive too. Null out big data you no longer need.

08

Objects & prototypes — "everything is an object"

JavaScript is a prototype-based language. There are no real classes underneath: every object has a hidden link, [[Prototype]] (exposed as __proto__ / Object.getPrototypeOf), to another object. When a property isn't found on an object, the engine follows that link — the prototype chain — until it reaches null.

  • Functions are objects — callable ones. That's why 10_classes_and_oop/Object.js can do multipleBy5.power = 2. They also get a .prototype object for use with new.
  • Arrays are objects with integer-like keys and a magic length (typeof [] === "object").
  • Primitives are not objects, but act like them: "hitesh".toUpperCase() temporarily wraps the string in a String object (spec: ToObject) to find the method on String.prototype. Engines skip the actual allocation.

Injecting methods into everything (and why seniors don't)

10_classes_and_oop/Prototype.js adds trueLength to String.prototype — instantly every string in the program has it. That's how polyfills work (adding missing standard methods to old browsers). But extending built-ins in your own code is risky:

  • SmooshGate (2018): MooTools had added a non-standard Array.prototype.flatten. When browsers shipped the real one, sites broke — so TC39 renamed the standard method to flat() (the one used in 02_basics/02_array.js).
  • Prototype pollution is a real security bug class: merging untrusted JSON like {"__proto__": {"isAdmin": true}} into an object can add isAdmin to every object.
  • Enumerable additions leak into every for…in (shown in §07).

The event loop — simulated step by step

JS runs on one thread with one call stack, yet it handles timers, clicks and network calls "at the same time". The trick: slow work is handed to the host (browser/Node, written in C++ with real threads). When that work finishes, the host puts your callback in a queue. The event loop moves callbacks onto the stack — only when the stack is empty.

Promises & async/await

  • The executor passed to new Promise(fn) runs synchronously, immediately.
  • .then() always returns a new promise, resolved with whatever your callback returns — that's what makes chaining in 09_advance_one/promises.js work. Forget the return and the next .then receives undefined.
  • Reactions are always run as microtasks, even if the promise is already settled.
  • async functions always return a promise; await x pauses the function and schedules the rest as a microtask when x settles.

XMLHttpRequest is the 2000s callback API: you watch readyState go 0 UNSENT → 1 OPENED → 2 HEADERS_RECEIVED → 3 LOADING → 4 DONE and parse responseText yourself. fetch is promise-based, streams the body (res.json() is itself async), supports AbortController for cancellation, and is available in Node ≥ 18 too. The heap & garbage collection

You never free() in JS. The engine periodically finds objects that can no longer be reached from a root (globals, the current call stack, active handles) and reclaims them. Reference counting is not used — it can't free cycles. Instead engines trace: mark everything reachable, then sweep (and sometimes compact) the rest.

Concepts you won't find (in this form) elsewhere

Prototype delegation. Objects inherit from other objects, live — add a method to Array.prototype and existing arrays get it instantly.
Run-to-completion. A function is never interrupted by another JS callback. No data races on the main thread, no locks — but one slow function freezes everything.
Dynamic this. Decided by the call site, not the definition (except arrows).
Two "empty" values and eight falsy values, plus type coercion that's fully specified (not undefined behavior).
Hoisting & TDZ. Declarations are processed before any code in their scope runs.
The host decides I/O. The language has no print, no file API, no event loop of its own.

16.1 · Every value is a tagged word: Smi or pointer

V8 doesn't store "a type field + a value" for each variable. A JS value is one machine word (or 32 bits with pointer compression, used by Chrome). The lowest bit says what it is. From include/v8-internal.h:

try 42, -7, 1073741823, 1073741824, 3.14, -0
  • Smi (small integer): the integer is stored shifted left by one, tag bit 0. No allocation at all; a + b on two Smis is a CPU add plus an overflow check. With 32-bit compressed tagged values that gives 31-bit Smis (−230 … 230−1). Node builds without pointer compression and keeps 32-bit Smis in the upper half of a 64-bit word.
  • Anything else (3.14, -0, big ints, NaN, strings, objects…) is a HeapObject: a pointer with tag bit 1. Numbers that don't fit become a boxed HeapNumber (optimized code can keep them unboxed in registers).
  • Every HeapObject's first field points to its Map — next.

Senior takeaway Avoid holes (new Array(n) then filling out of order, delete arr[i], writing past the end), don't mix types in hot numeric arrays, and prefer typed arrays (Float64Array) for large numeric data. Array.from({length: n}, …) or push keep arrays packed.

16.5 · Oddballs — why typeof null === "object"

In the first JS engine (1995), values carried a small type tag; objects had tag 0 and null was the C NULL pointer (all zeros) — so typeof read tag 0 and said "object". A 2006 proposal to make typeof null === "null" was rejected because it broke existing sites. In V8 today null, undefined, true and false are singleton heap objects called Oddballs, and each one simply stores its typeof answer (src/objects/oddball.h):

So the "weird" table from §04 is literally data: null's to_number_ is 0 (hence null >= 0), undefined's is NaN.

16.6 · Strings, builtins & the microtask queue

String representations (src/objects/string.h)

  • SeqOneByteString / SeqTwoByteString: flat Latin-1 or UTF-16 buffer
  • ConsString: a + b makes a rope node pointing at both halves — so str += x in a loop is cheap; it's flattened on first indexed read
  • SlicedString: slice/substring can point into the parent instead of copying
  • ThinString / internalized strings: property keys are deduplicated so comparing keys is a pointer compare

Builtins in Torque

Most of Array.prototype, Promise and friends are written in Torque, which compiles to the same machine code as the rest of V8. Array.prototype.sort is TimSort (third_party/v8/builtins/array-sort.tq) since V8 7.0, and stable since ES2019. Promise logic lives in src/builtins/promise-*.tq; resolving a promise enqueues a PromiseReactionJobTask on the microtask queue.

The microtask queue itself (src/execution/microtask-queue.h) is a ring buffer:

The big reveal V8 owns the microtask queue, but has no task queue and no event loop. Chrome's Blink scheduler and Node's libuv run the loop and call PerformCheckpoint() after each task. That's why setTimeout works differently in browsers and Node — it isn't part of V8 or the ECMAScript spec at all.
